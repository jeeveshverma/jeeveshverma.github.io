Fuzzing
validators_

A validator is a promise about what gets past it. Example-based tests check the inputs I thought of. A fuzzer checks the promise against inputs I didn't, and Go has one built into go test.

01Assert properties, not outputs

A normal test says: for this input, expect that output. A fuzzer generates thousands of inputs per second, so you can't write the expected output for each one. You write a property instead: something that must hold for every input.

For a validator, the property almost writes itself:

Rejection is always acceptable. Acceptance has to be earned.

If the validator says no, the test returns early; being too strict is a product question, not a safety one. If it says yes, the test independently checks that the accepted value really is safe. A validator that lets through one bad input in a million fails here, and a fuzzer is very good at finding the one in a million.

The two properties for linkforge's vanity-code validator are "within length bounds" and "only allowed characters":

linkforge/internal/shortener/fuzz_test.go
// FuzzValidateCustomCode asserts validateCustomCode never panics and only
// accepts codes within the length bounds using the allowed charset.
func FuzzValidateCustomCode(f *testing.F) {
    for _, s := range []string{"", "ab", "abc", "my-vanity_1", "WithCAPS", strings.Repeat("a", 33), "bad char", "emoji😀"} {
        f.Add(s)
    }
    f.Fuzz(func(t *testing.T, code string) {
        if err := validateCustomCode(code); err != nil {
            return
        }
        if len(code) < minCodeLength || len(code) > maxCodeLength {
            t.Fatalf("accepted code %q outside length bounds", code)
        }
        for _, r := range code {
            ok := strings.ContainsRune(alphabet, r) || r == '-' || r == '_'
            if !ok {
                t.Fatalf("accepted code %q with disallowed rune %q", code, r)
            }
        }
    })
}
Check it a different way

The property check should not call the validator's own helpers. Here it re-checks the charset rune by rune against the alphabet. If it reused the validator's logic, a bug in that logic would pass its own test.

02Fuzzing a URL normaliser

URLs are where validators go to die. Schemes in odd cases, userinfo, missing hosts, scheme-relative links, javascript:, non-ASCII hosts. linkforge's normalizeURL promises that anything it accepts is a parseable absolute http(s) URL with a host, under the length limit. The fuzz target spells that promise out, one property per check:

linkforge/internal/shortener/fuzz_test.go
f.Fuzz(func(t *testing.T, raw string) {
    got, err := normalizeURL(raw)
    if err != nil {
        return // rejection is always acceptable
    }
    u, perr := url.Parse(got)
    if perr != nil {
        t.Fatalf("accepted %q -> unparseable %q: %v", raw, got, perr)
    }
    if scheme := strings.ToLower(u.Scheme); scheme != "http" && scheme != "https" {
        t.Fatalf("accepted non-http(s) scheme %q from input %q", u.Scheme, raw)
    }
    if u.Host == "" {
        t.Fatalf("accepted hostless URL %q from input %q", got, raw)
    }
    if len(got) > maxURLLength {
        t.Fatalf("accepted over-length URL (%d) from input %q", len(got), raw)
    }
})

Notice what's checked: the output, got, not the input. A normaliser transforms what it's given, so the promise is about what comes out. Parsing got again also catches a quieter bug class: output that doesn't survive a round trip.

And there's an implicit property in every fuzz target: it must not panic. Any panic inside f.Fuzz is a failure, so even a target with no assertions at all is worth having.

03Choosing seeds

Seeds added with f.Add are the starting corpus. The fuzzer mutates them, so good seeds put it near the interesting boundaries from the start. Here are the URL seeds:

linkforge/internal/shortener/fuzz_test.go
seeds := []string{
    "https://example.com",
    "http://a.b/c?d=1#frag",
    "HTTPS://EXAMPLE.COM/Path",
    "https://user:pass@host:8080/p",
    "",
    "   ",
    "not a url",
    "ftp://example.com",
    "javascript:alert(1)",
    "http://",
    "//no-scheme",
    "https://例え.テスト/страница",
}

I pick them the way I'd pick manual test cases, by category:

  • Valid, in several shapes: query and fragment, upper-case scheme, userinfo and port.
  • Empty and whitespace: the cheapest bugs to have and to catch.
  • Wrong scheme: ftp, and javascript: because that one matters for security.
  • Almost valid: a scheme with no host, a host with no scheme.
  • Non-ASCII: so the mutator starts with multi-byte runes instead of having to discover them.

Seeds also run as ordinary test cases in every plain go test, without -fuzz. If the fuzzer ever finds a failure, Go writes the input to testdata/fuzz/, and from then on it's a permanent regression test.

04Beyond validators

Anything with a promise about its output range can be fuzzed. In workq, the retry backoff promises its delay is never negative and never exceeds the cap plus jitter, for any attempt number:

workq/fuzz_test.go
f.Fuzz(func(t *testing.T, attempt int, baseMs, maxMs int64, jitterPct int) {
    // Keep inputs in a sane, checkable range.
    if baseMs < 0 || maxMs <= 0 || baseMs > 1_000_000 || maxMs > 1_000_000_000 {
        return
    }
    jitter := float64(((jitterPct%101)+101)%101) / 100 // 0..1

    b := Backoff{
        Base:   time.Duration(baseMs) * time.Millisecond,
        Max:    time.Duration(maxMs) * time.Millisecond,
        Factor: 2,
        Jitter: jitter,
        Rand:   func() float64 { return 1 }, // maximum positive jitter
    }
    d := b.Delay(attempt)
    if d < 0 {
        t.Fatalf("negative delay %v for attempt=%d base=%dms max=%dms jitter=%.2f", d, attempt, baseMs, maxMs, jitter)
    }
    upper := time.Duration(float64(b.Max)*(1+jitter)) + time.Millisecond
    if d > upper {
        t.Fatalf("delay %v exceeds cap+jitter %v", d, upper)
    }
})

Two techniques worth stealing: fold raw inputs into a valid range (jitterPct becomes 0–100% whatever the fuzzer sends) instead of rejecting most of them, and pin randomness to the worst case (Rand returns 1) so the bound is tested at its edge.

The simplest target in the repo has no assertion at all. It feeds arbitrary bytes to the typed JSON handler and relies on the implicit property: malformed payloads must come back as errors, not crashes.

workq/fuzz_test.go
f.Fuzz(func(t *testing.T, data []byte) {
    // Must not panic; an error return is acceptable.
    _ = h(context.Background(), Job{Kind: "x", Payload: data})
})

05A fuzz smoke run in CI

Fuzzing is open-ended; left alone, it runs until it finds something. In CI I give each target a fixed budget. Twenty seconds won't find deep bugs, but it does catch a change that breaks a property in an obvious way, on every push:

linkforge/.github/workflows/ci.yml
fuzz:
  name: Fuzz (smoke)
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-go@v5
      with:
        go-version: "1.23"
        cache: false
    - name: Fuzz URL normalizer
      run: go test -run='^$' -fuzz=FuzzNormalizeURL -fuzztime=20s ./internal/shortener/
    - name: Fuzz custom-code validator
      run: go test -run='^$' -fuzz=FuzzValidateCustomCode -fuzztime=20s ./internal/shortener/
  • -run='^$' skips the regular tests, which already ran in the test job.
  • -fuzz accepts only one target per invocation, hence one step per target.
  • It's a separate job, so a fuzz failure shows up as its own red check rather than burying itself in the unit-test output.

For a longer hunt, run the same command locally with a bigger -fuzztime and leave it going.

06Takeaways

  1. Write the promise, not the answer. For a validator: if it accepts, the value must be safe. Rejecting is always fine.
  2. Check acceptance independently of the validator's own code, and check the transformed output, not the raw input.
  3. Seed by category: valid shapes, empty, wrong scheme, almost valid, non-ASCII.
  4. "Must not panic" is a property too. A fuzz target with no assertions still earns its place on any parser.
  5. Give CI a fixed fuzz budget as its own job, and let crashers in testdata/fuzz/ become permanent regression tests.
