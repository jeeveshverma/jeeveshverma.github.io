Testing time
without sleeping_

Expiry, background reapers, rate-limit refill, retry backoff: all of it depends on the clock. If your tests depend on the real clock, they're slow and they flake. Here's how I take the clock away from the code and hand it to the test.

01The problem with Sleep

The obvious way to test "a link expires after an hour" is to create a link with a short TTL, time.Sleep past it, and check it's gone. It works on your laptop. Then it meets a busy CI runner.

  • It's slow. Every sleep is dead time, multiplied by every test that does it.
  • It's flaky. Sleep long enough to be safe and the suite crawls; sleep short and a loaded machine misses the window.
  • It can't reach the interesting cases. "One token refills after exactly 100ms" or "the delay caps at attempt 4" are hard to hit with a wall clock.

The fix in both of my Go side projects, linkforge and workq, is the same: the code never calls time.Now() directly.

02Make time a field

linkforge's rate limiter keeps a token bucket per client. The only change needed to make it testable is that "now" is a function stored on the struct, defaulting to the real clock:

linkforge/internal/ratelimit/limiter.go
type Limiter struct {
    rps   float64
    burst float64

    mu      sync.Mutex
    buckets map[string]*bucket
    now     func() time.Time
}

func NewLimiter(rps float64, burst int) *Limiter {
    return &Limiter{
        rps:     rps,
        burst:   float64(burst),
        buckets: make(map[string]*bucket),
        now:     time.Now,
    }
}

Production gets time.Now. The test, which lives in the same package, swaps in a closure over a local variable, and then moves time by assigning to that variable:

linkforge/internal/ratelimit/limiter_test.go
func TestLimiterRefillsOverTime(t *testing.T) {
    l := NewLimiter(10, 5) // 10 tokens/sec => 1 token per 100ms
    now := time.Unix(0, 0)
    l.now = func() time.Time { return now }

    for i := 0; i < 5; i++ {
        l.Allow("client")
    }
    if l.Allow("client") {
        t.Fatal("request allowed before refill, want denied")
    }

    now = now.Add(100 * time.Millisecond) // one token refilled
    if !l.Allow("client") {
        t.Error("request denied after refill, want allowed")
    }
    if l.Allow("client") {
        t.Error("second request allowed, only one token should have refilled")
    }
}

That test checks an exact boundary (one token, not zero, not two) and finishes in microseconds. No interface, no mocking library: a func() time.Time is the smallest seam that works.

Why not a global?

A package-level var now = time.Now also works, but tests that swap it can't run in parallel and leak into each other. A field keeps each test's clock private to the instance it built.

03Expiry in one line

The same trick turns a TTL test into straight-line code. The shortener service and the store both take a clock, the test points them at the same variable, and "two hours later" is an assignment:

linkforge/internal/shortener/service_test.go
base := time.Date(2026, 7, 26, 12, 0, 0, 0, time.UTC)
clock := base
svc.now = func() time.Time { return clock }
store.SetClock(func() time.Time { return clock })

link, _, err := svc.Shorten(context.Background(), ShortenRequest{URL: "https://example.com", TTL: time.Hour})
// ...
if want := base.Add(time.Hour); !link.ExpiresAt.Equal(want) {
    t.Errorf("ExpiresAt = %v, want %v", link.ExpiresAt, want)
}
if _, err := svc.Resolve(context.Background(), "ttl0001"); err != nil {
    t.Fatalf("Resolve() before expiry error = %v", err)
}
clock = base.Add(2 * time.Hour)
if _, err := svc.Resolve(context.Background(), "ttl0001"); !errors.Is(err, storage.ErrNotFound) {
    t.Fatalf("Resolve() after expiry error = %v, want ErrNotFound", err)
}

A fixed time.Date also makes the expected values exact. ExpiresAt is checked with Equal against a known instant instead of "roughly an hour from whenever the test ran".

04Pass "now" in

Sometimes there's an even simpler seam: make the time an argument. linkforge's store doesn't decide when "now" is during a sweep; the caller tells it.

linkforge/internal/storage/storage.go
// DeleteExpired removes links that have expired as of now and returns the
// number removed.
DeleteExpired(now time.Time) int

So the sweep logic is tested with plain values, no clock swapping at all:

linkforge/internal/storage/memory_test.go
base := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
// "keep" has no expiry; "drop" expires at base
if n := s.DeleteExpired(base.Add(time.Second)); n != 1 {
    t.Errorf("DeleteExpired() = %d, want 1", n)
}

The rate limiter's idle-bucket cleanup does the same thing: l.sweep(base.Add(time.Minute), 30*time.Second) asks "as of minute one, reclaim anything idle for more than 30 seconds" and expects exactly one bucket back.

The background reaper that calls DeleteExpired on a ticker is then a thin loop. Its tests only need to prove the wiring: it sweeps, and it stops when the context is cancelled.

05Randomness is time's cousin

Retry backoff has the same problem from a different direction. workq's backoff adds jitter so a batch of jobs that failed together don't all retry in lockstep. Jitter means randomness, and randomness in a test means assertions like "somewhere between 80 and 120ms".

So the random source is a seam too:

workq/backoff.go
// Rand returns a value in [0,1). It is a seam for deterministic tests; nil
// uses the default source.
Rand func() float64

Pinning it to the extremes turns a fuzzy range into two exact assertions:

workq/backoff_test.go
// A fixed Rand of 1.0 yields the maximum positive perturbation (+Jitter);
// 0.0 yields the maximum negative (-Jitter).
base := 100 * time.Millisecond

high := Backoff{Base: base, Max: time.Second, Factor: 1, Jitter: 0.2, Rand: func() float64 { return 1 }}
if got, want := high.Delay(1), 120*time.Millisecond; got != want {
    t.Errorf("Delay with rand=1 = %v, want %v", got, want)
}

low := Backoff{Base: base, Max: time.Second, Factor: 1, Jitter: 0.2, Rand: func() float64 { return 0 }}
if got, want := low.Delay(1), 80*time.Millisecond; got != want {
    t.Errorf("Delay with rand=0 = %v, want %v", got, want)
}

And because Delay just returns a duration instead of sleeping for it, the exponential curve and the cap are a table test with no waiting at all: attempts 1–5 give 100, 200, 400, 400, 400ms.

06Where I still wait

I want to be honest about the edges. A few workq tests still use a short time.Sleep, and they have something in common: they test a goroutine handoff, not a duration.

workq/memqueue_test.go
go func() {
    _, err := q.Pop(ctx)
    errc <- err
}()
time.Sleep(10 * time.Millisecond) // let the goroutine block in Pop

if err := q.Close(); err != nil {
    t.Fatalf("Close error = %v", err)
}

There's no clean way to observe "this goroutine is now parked inside Pop" from outside. The sleep makes the interesting interleaving likely, and the test still passes if it doesn't happen (Close-then-Pop also returns ErrClosed). What matters is that the assertion never depends on timing: it waits on a channel with a generous time.After(time.Second) as a failure deadline, not as the expected path.

The other trick for queues is to make "the future" far enough away that nothing can reach it. To test that a ready low-priority job beats a high-priority one that isn't due yet, workq schedules the high-priority job an hour out. Nothing waits for that hour; it just guarantees the ordering.

07Takeaways

  1. Never call time.Now() deep in logic. Store a now func() time.Time on the struct, defaulting to time.Now.
  2. Prefer passing time in (DeleteExpired(now)) when the caller already knows it. No clock to swap at all.
  3. Return durations, don't sleep them. A backoff that returns a delay is a pure function you can table-test.
  4. Treat randomness like time: inject it, and pin it to the extremes in tests.
  5. When you must wait, wait on a signal. Use channels for the happy path and time.After only as a failure deadline.
A test that sleeps is asking the machine for a favour. A test with an injected clock is giving it an instruction.
